# 애드로그 API 수집

2026-09-21

## 왜

매장 하나를 채우는 데 10분이 넘는다. 애드로그에서 PDF를 내보내고, 캡처를
네댓 장 찍고, 오픈업에서 세 장 더 찍고, 올려서 판독을 기다리고, 눈으로
대조한 뒤 저장을 누른다. 14곳이면 두 시간이 넘고 다음 달에 또 한다.

그래서 안 한다. 매장 14곳 중 스냅샷이 있는 곳은 3곳, 기획안이 있는 곳도
3곳, 플레이스URL이 든 곳도 3곳이다. 나머지 11곳은 등록만 되고 한 번도
안 돌았다.

쌓인 스냅샷도 성한 게 아니다. 16건 중 값이 든 건 5건이고 나머지 11건은
수집시각만 있는 빈 껍데기다. 전부 2026-08-10~08-18 한 주에 몰려 있고
그 뒤로는 한 건도 없다. "쌓인 스냅샷이 재계약 자리에서 성과의 증거가
된다"는 전제가 실제로는 안 돌아간다.

한편 애드로그 계정에는 키워드 951개, 플레이스 206곳이 이미 등록돼 있다.
고객사 14곳 중 12곳이 그 안에 있고, 로얄피그 한남점은 키워드가 57개다.
사람이 손으로 찍어 올리는 캡처의 대부분은 이미 API로 받을 수 있는 값이다.

## 확인된 API

문서: https://www.adlog.kr/api/doc/ · 호출: `https://api.adlog.kr/api/`

인증은 `authorization: Bearer <키>` 헤더, 본문은 JSON POST다.
`user_id`(회원 아이디)와 `api_menu`(플레이스=1064)가 모든 요청에 들어간다.
HTTP 는 200 으로 오고 성패는 본문 `code` 에 실린다 — `0000` 이 성공이다.

| 엔드포인트 | 주는 것 |
|---|---|
| `getKeywordList.php` | api_no, place_id, place_name, keyword, month_count, detail_keyword |
| `getKeywordListDetail.php` | rank_date, rank_num, 리뷰수, 저장수, place_count, place_n1~n3 |

순위는 최대 3개월, 한 페이지 30건, 5페이지까지 본다. 2026-09-19 에
호출해 당일 순위가 내려오는 것을 확인했다. 계정은 실사용 전환 상태다.

일일 호출 한도는 슬롯 수 × 20 이다. 슬롯 951 개이므로 19,020 회.

### 캡처 판독과의 대조

| 값 | 캡처 판독 | API |
|---|---|---|
| 플레이스ID·명 | O | O |
| 리뷰수·저장수 | O | O |
| 키워드 순위 | 일부만 (48개 중 17개) | 전량 |
| 월 조회수 | O | O |
| 시점 | 기준일·비교일 2개 | 최대 3개월 일자별 |
| 경쟁업체 수 | X | O |
| 플레이스 지수 N1~N3 | X | O |
| 업종(카테고리) | O | X |
| 히든키워드 | O | X |
| 리뷰 목록 | O | X |

API 가 대부분 우위다. 특히 사용법 문서가 "원리상 일부만 들어온다"며
감수하라고 적어 둔 순위 누락이 사라진다. API 가 못 주는 셋(업종·
히든키워드·리뷰 목록)만 캡처 판독에 남긴다.

## 범위

**한다**

- 애드로그 API 클라이언트 신설
- 고객사와 애드로그 등록분을 화면에서 잇기
- 순위를 일자별 원장으로 쌓기
- 갱신 끝에 스냅샷 한 건 파생
- 제안서로 안 건너가던 총키워드·TOP3·TOP10 을 잇기 (아래 "발견된 버그")

**안 한다**

- 키워드 등록(`createKeyword`) — 슬롯을 먹고 삭제에 월 한도가 있다.
  되돌리기 어려운 일은 사람이 애드로그 화면에서 한다
- 재검색 요청(`researchKeyword`) — 일일 한도가 따로 있다. 필요해지면 그때
- 캡처 판독 제거 — 업종·히든키워드·리뷰 목록은 API 에 없다
- 오픈업 — API 가 없다. 캡처 판독 그대로
- 성과 리포트 — 다음 회차. 이번에 쌓는 원장이 그 재료다

## 설계

### 모듈 경계

`lib/adlog.py` 를 새로 둔다. 애드로그 API 만 아는 층이다. 엔드포인트,
에러코드 표, 페이징을 여기서 끝낸다. 고객사도 스냅샷도 모른다.

`lib/collect.py` 는 지금 역할을 지킨다. 수집을 조율하고 `adlog` 를
호출한다. 모듈 상단 세 원칙(사무실에서 한다 · 실패해도 안 막힌다 ·
수집 시각을 함께 저장한다)은 그대로다. 추정값 경고 상자는 지운다 —
추정이 아니게 됐다.

`lib/storage.py` 가 `ranks.json` 경로를 아는 유일한 곳이다. "경로를 아는
유일한 모듈"이라는 기존 약속을 깨지 않는다.

`server.py` 는 라우트만 연다. 계산은 두지 않는다.

### 연결 키

`place_id` 로 잇는다. 그룹은 쓰지 않는다.

그룹 91종 중 79종이 플레이스 한 곳이라 매장 단위로 쓰이는 듯 보이지만
일관되지 않다. 방이점과 지리산꿀통갈비는 `기본` 에 섞여 있고, 로얄피그
한남점은 `로얄피그 한남점`·`기본`·미지정 셋에 흩어져 있다. 담당자 이름을
단 그룹(`김대한` 12곳, `김시완` 11곳)도 있다. place_id 는 흔들리지 않는다.

### 저장 구조

`client.json` 에 연결 정보를 단다.

```json
"애드로그": {
  "플레이스ID": "2069074461",
  "플레이스명": "미친양꼬치 잠실점",
  "연결시각": "2026-09-21T14:30:00",
  "키워드": [{"api_no": 2978093, "keyword": "잠실새내 맛집"}]
}
```

`api_no` 를 박아 두는 이유는 순위 조회가 그 번호 단위라서다. 없으면
갱신할 때마다 951 건을 훑어야 한다.

순위는 매장별 `data/clients/{slug}/ranks.json` 에 쌓는다.

```json
{
  "플레이스ID": "2069074461",
  "갱신시각": "2026-09-21T14:30:00",
  "키워드": {
    "잠실새내 맛집": {
      "api_no": 2978093,
      "월검색수": 22160,
      "경쟁업체수": 2520,
      "순위": {"2026-09-19": 26, "2026-09-18": 27, "2026-09-17": 26}
    }
  },
  "매장지표": {
    "2026-09-19": {"방문자리뷰": 895, "블로그리뷰": 619, "저장수": "8,000+"}
  }
}
```

날짜를 키로 쓴다. 같은 날 몇 번을 눌러도 덮어쓰기라 중복이 안 생긴다.
빈 껍데기 11건이 쌓인 경로가 여기서 막힌다.

매장지표를 키워드 밖으로 뺀 건 API 가 키워드마다 같은 리뷰수를
되돌려주기 때문이다. 키워드 아래 두면 같은 값이 57 벌 복사된다.

`저장수` 는 문자열로 온다(`"8,000+"`). **원장에는 원문 그대로 둔다** —
`8000` 으로 적으면 8,000 이상이라는 사실이 사라진다. 스냅샷에는 숫자만
뽑아 넣는다(아래 "발견된 버그" 참고).

### 연결 흐름 (매장당 한 번)

1. 매장 정보 패널에서 `애드로그에서 찾기`
2. 등록 목록이 뜬다. 매장 이름으로 후보를 추려 위에 올린다.
   플레이스URL 이 이미 있으면 그 place_id 를 미리 고른다
3. 고르면 `client.json` 에 애드로그 블록이 붙는다. 플레이스URL·업종이
   비어 있으면 같이 채운다 — `merge_into_client` 의 "빈 칸만 채운다"를 따른다

하루인 정자본점처럼 후보가 여럿인 건(`하루인`·`하루인 인계직영점`·
`하루인 판교직영점`) 사람이 고른다. 이름이 비슷하다고 도구가 정하지 않는다.

목록 조회는 50 개씩 끊어 20 회다. 매번 하면 낭비라
`data/_cache/adlog_places.json` 에 받아 두고 하루가 지나면 다시 받는다.
목록 화면에 새로고침을 단다. `.gitignore` 에 `data/_cache/` 를 더한다.

### 갱신 흐름 (누를 때마다)

1. `순위 갱신` 을 누른다
2. 연결된 키워드마다 순위를 받아 `ranks.json` 에 쓴다
3. 최신 날짜 값으로 스냅샷 한 건을 파생한다

호출은 키워드 수만큼이다. 로얄피그 57 회가 가장 많고 연결된 10 곳을 다
돌려도 143 회다. 한도 19,020 회에 견주면 여유가 크다. 호출 사이에 간격을
두고 진행 상태를 보여준다.

**값이 하나도 없으면 스냅샷을 안 쌓는다.** 지금 빈 껍데기가 생긴
경로다. 수집시각만 든 스냅샷은 증거가 아니라 잡음이다.

버튼은 매장 정보 패널 안에만 둔다. 구성판에는 올리지 않는다. 미팅
중에는 네트워크를 안 쓴다.

### 스냅샷 파생 규칙

제안서가 읽는 모양을 그대로 만든다. `proposal._metrics` 는 최신
스냅샷에서 `플레이스`·`순위`·`순위요약` 을 읽는다. 구조를 바꾸면
제안서 네 쪽이 전부 흔들린다.

```json
{
  "수집시각": "2026-09-21T14:30:00",
  "플레이스": {"방문자리뷰": 895, "블로그리뷰": 619, "저장수": "8,000+"},
  "순위": [{"키워드": "잠실새내 맛집", "순위": 26}],
  "순위요약": {"총키워드": 7, "TOP3": 0, "TOP10": 2},
  "예상매출": null
}
```

- `순위` 의 각 줄은 **키워드별 가장 늦은 `rank_date`** 값이다.
  키워드마다 마지막 체크일이 다를 수 있어 한 날짜로 못 자른다
- `순위요약.총키워드` 는 연결된 키워드 수, `TOP3`·`TOP10` 은 그중
  순위가 3 이하·10 이하인 수다
- `예상매출` 은 건드리지 않는다. 오픈업 몫이다

안 쌓는 조건은 `proposal._has_data` 의 판정을 그대로 뒤집어 쓴다 —
순위가 0 건이고 플레이스 값이 전부 `None` 이면 쌓지 않는다. 두 곳이
서로 다른 기준을 쓰면 "쌓았는데 제안서가 못 본다"가 생긴다.

### 기존 추적키워드와의 관계

`추적키워드` 는 건드리지 않는다. 애드로그가 연결되면 순위는 그쪽에서
오고, 추적키워드는 애드로그에 없는 키워드를 손으로 보는 경로로 남는다.

방이점의 `방이맛집`(손입력)과 `방이동 맛집`(애드로그)은 다른 키워드로
둔다. 억지로 맞추면 어느 쪽이 진짜인지 모르게 된다. 제안서는 둘을 합쳐
본다.

### 발견된 버그 — 같이 고친다

스펙을 쓰다 둘을 찾았다. 둘 다 API 를 붙이는 순간 바로 걸린다.

**1. 총키워드·TOP3·TOP10 이 제안서에 안 나간다.**

`read_doc._snapshot()` 은 `순위요약` 에 쓰는데 `proposal._search()` 는
`진단` 에서 읽는다. 키가 어긋나 값이 건너오지 않는다. 잠실점 실데이터로
확인했다.

```
스냅샷에 든 값:  {'총키워드': 48, 'TOP3': 1, 'TOP10': 15}
제안서 검색 장:  [{'이름': '방문자 리뷰', ...}, {'이름': '저장수', ...}]
```

사용법 문서가 "미팅에서 할 말은 이쪽"이라고 짚은 숫자다. `proposal.py`
주석은 "여기서 쓴다"고 적어 뒀지만 실제로는 안 쓴다.

테스트가 못 잡은 이유는 `test_proposal.py` 가 `"진단": {"총키워드": 47}`
로 가짜 스냅샷을 만들기 때문이다. 생산 코드가 만드는 모양이 아니다.

고치는 쪽은 `proposal.py` 다. 총키워드·TOP3·TOP10 은 순위 요약이지
시점 사실이 아니므로 `순위요약` 이 제 자리다. `진단` 블록은 기준일·
비교일·대표키워드·히든키워드·리뷰를 담는 자리로 둔다. 테스트도 실제
스키마로 맞춘다.

**2. 애드로그 저장수가 제안서를 터뜨린다.**

`proposal._search()` 는 `f"{int(값):,}개"` 로 찍는다. API 가 주는
`"8,000+"` 가 들어오면 `ValueError` 로 제안서 생성이 통째로 실패한다.
지금은 판독기가 숫자를 넣어 안 터진다.

원장에는 원문을 두고 스냅샷에는 숫자만 뽑아 넣는다. 쉼표와 `+` 를 떼고
정수로 읽되, 못 읽으면 `None` 이다. `proposal.py` 의 표기는 건드리지
않는다 — 종이에 `8,000개` 로 찍히는 건 실제보다 낮은 수이지 거짓이
아니고, "이상"은 원장에 남아 성과 리포트에서 쓴다.

### 에러 처리

HTTP 200 에 `code` 로 실패가 온다. `code != "0000"` 을 먼저 본다.

| 코드 | 화면에 뜨는 말 |
|---|---|
| 4000·4001·4002 | 애드로그 계정 정보를 확인하십시오 |
| 4003·4100 | 메뉴 코드가 잘못됐습니다 |
| 4004 | 이 PC 의 IP 를 애드로그에 등록해야 합니다 |
| 4009 | 애드로그 서비스 기간이 만료됐습니다 |
| 2000 | 조회할 키워드 번호가 없습니다 |
| 2001 | 데이터 없음 — 실패가 아니다. 아직 순위가 안 잡힌 새 키워드다 |

원문은 stderr 로만 보낸다. 예외 문구를 저장물에 넣지 않는다는
`short_error` 의 기존 규칙을 잇는다. 키나 아이디가 없으면 조용히
건너뛰고 나머지 수집은 계속한다.

키워드 하나가 실패해도 나머지는 계속 본다. 열 개 중 하나 때문에 아홉
개를 못 보면 그날 미팅 자료가 통째로 빈다.

### 환경변수

```
ADLOG_API_KEY=   # 발급받은 키
ADLOG_USER_ID=   # 애드로그 회원 아이디
```

둘 다 `.env` 에서 읽는다. `.env.example` 에 이름표만 둔다.

## 테스트

`tests/test_adlog.py` 신규:

- 응답 파싱 — 순위·리뷰수·저장수 문자열
- `code` 분기 — 성공, 인증 실패, 2001(데이터 없음)을 실패로 안 봄
- 페이징 종료 조건 — `total_count` 를 채우면 멈춘다
- https 강제 — 평문 http 면 요청을 만들지 않는다
- 키·아이디가 없으면 조용히 통과하고 나머지는 계속한다
- 키워드 하나가 실패해도 나머지가 남는다

`ranks.json`:

- 멱등성 — 같은 날짜를 두 번 써도 한 건이다
- 빈 결과면 스냅샷을 안 쌓는다
- 저장수 `"8,000+"` 가 원장에는 원문으로, 스냅샷에는 `8000` 으로 간다

실제 네트워크를 타는 검증은 기존 관행대로 `-m network` 하나로 둔다.

`tests/test_collect.py` 는 엔드포인트와 필드 기대값을 고친다.

`tests/test_proposal.py` 는 가짜 스냅샷을 `read_doc._snapshot()` 이
실제로 만드는 모양으로 바꾼다. 총키워드·TOP3·TOP10 이 제안서 검색 장에
찍히는지 보고, 저장수에 문자열이 들어와도 안 터지는지 본다.

## 인수 기준

1. 매장 정보 패널에서 애드로그 등록분을 골라 매장에 이을 수 있다
2. `순위 갱신` 한 번으로 그 매장 키워드 순위가 `ranks.json` 에 들어온다
3. 같은 날 두 번 눌러도 원장이 한 벌이고 스냅샷도 한 건이다
4. 값이 안 온 매장은 스냅샷이 안 쌓인다
5. 키를 지우면 순위 조회만 건너뛰고 나머지 수집은 그대로 돈다
6. 애드로그가 죽어도 손입력 경로가 그대로 열려 있다
7. 제안서 검색 장에 총키워드·TOP3·TOP10 이 찍힌다 (버그 1)
8. 저장수가 `"8,000+"` 로 와도 제안서가 나온다 (버그 2)
9. 기존 테스트가 전부 통과한다
